# Phase 7 evaluation protocol (pre-registered)

This file, the scenarios, the oracle and the frozen prompt are committed **before any result file exists**. Results are reported as they come out.

## 1. Question
Hackathon rule: "if the product still works once FalkorDB is taken out, the graph is decoration." We ask what the graph contributes by scoring three configurations against an independent oracle on 24 scenarios.

## 2. Configurations
| id | name | what it knows | what it does |
|---|---|---|---|
| A | GraphDispatch | the FalkorDB graph `sjfd_test` (roads, stations, units, hospitals, hazards, memory) | `ops.run_call` (create incident, recall, recommend with `effective_requirements` and `algo.SPpaths`, record decision); no dispatch |
| B | Straight-line | the seed tables only (stations, units, hospitals, incident types); no road network, no address memory, no hazard knowledge | nearest by straight line, see section 5 |
| C | LLM with facts as text | Claude Haiku 4.5 gets every fact as text in one prompt (section 6) but no road network | one forced tool call, see section 6 |

The comparison is deliberately about what the graph adds: road travel times, hazard-driven requirements and address memory enforced by queries. B and C get the same tables as text or arrays; C also gets the active hazards and prior incidents at the address as text (the memory is handed to it, so any C failure on memory is not a missing-data failure).

## 3. Scenarios (eval/scenarios.json, 24, generated by eval/make_scenarios.py with `random.Random(42)`)
- S1 stroke (37.3300,-121.9300); S2 burn east (37.3600,-121.8550); S3 pediatric trauma (37.3100,-121.8600); S4 hazmat spill (37.3200,-121.9100); S5 structure fire (37.3450,-121.8800).
- O1 structure fire and O2 cardiac arrest, both at address "200 Demo St" (37.3360,-121.8900). O1 has an active `oxygen_storage` hazard at the address and no earlier incidents. O2 runs after O1: the hazard is still active and O1 (a structure fire) is an earlier incident at the address. For O1 the hazard-added unit (HM26) is required; for O2 the memory must be recalled (oxygen_storage adds nothing to a cardiac arrest).
- R01 to R17: 17 points sampled uniformly inside box B2 (W -121.945 S 37.300 E -121.840 N 37.370), rejected unless the nearest routable intersection is within 300 m (haversine) and the second nearest is at least 1 m farther (so snapping cannot be ambiguous). Incident types cycle through structure_fire, cardiac_arrest, stroke, major_trauma, pediatric_trauma, burn, hazmat_spill.
- Unit state: every unit is available (the seed status `busy` for E1 and M1 is overridden for the evaluation) except the `busy_units` listed in a scenario. Two scenarios have their nearest needed unit busy: S5 (E8) and R02 (E4); each is the oracle's fastest chosen unit when everyone is available.
- Each scenario that is not O1/O2 uses its own address label so graph memory cannot leak between scenarios.

## 4. Oracle (eval/oracle.py)
Standard library and networkx only; it reads the seed CSVs only (road snapshot, stations, units, hospitals, incident types, hazard rules) and must not import `graphdispatch` (a test checks this). Written definitions it implements:
1. Snap the incident, every station and every hospital to the nearest intersection by haversine distance.
2. Travel time is the Dijkstra shortest path on `travel_s` over directed roads (station intersection to incident; incident to hospital).
3. Effective requirements: the incident type's requirements, plus for each active hazard kind the capability additions of the matching hazard rule rows; per (capability, hazard kind) the maximum count, then summed with the base. A kind listed twice counts once.
4. Units: for each needed capability, candidates are available units with the capability. Process capabilities scarcest first (fewest candidates, ties alphabetical). For each, take the fastest candidates (ties by unit id) not already used; a unit is used once. Shortfalls are reported as unmet.
5. Hospital: if the incident type has a destination capability, take the hospital offering it with the smallest travel time (ties by osm id). For a stroke, apply the bypass rule from incident_types.csv: use the fastest `stroke_thrombectomy` hospital only if its time minus the fastest `stroke_primary` hospital's time is at most 1800 s and its own time is at most 2700 s, otherwise the fastest `stroke_primary` hospital.
6. Memory: the active hazard kinds and earlier incident types given in the scenario.
The oracle has unit tests on numbers the advisor confirmed independently: S1 E7/M7 132 s, Regional 551 s, O'Connor 49 s, Santa Clara Valley 140 s; at 37.336,-121.89 T1 47 s, HM26 429 s, O'Connor 352 s.

## 5. Configuration B (eval/baselines.py)
Same assignment procedure as the oracle (steps 4 and 5) with two differences: (a) time = haversine distance / 13.4 m/s instead of road time, for stations to the incident and for the incident to hospitals, including inside the stroke rule; (b) B has no address memory and no hazard knowledge, so it uses the base requirements only and reports no recalled facts.

## 6. Configuration C (eval/prompt.py, eval/prompt_template.txt)
- Model: `us.anthropic.claude-haiku-4-5-20251001-v1:0` (env BEDROCK_MODEL_ID), region us-east-1, Bedrock Converse API through `graphdispatch/llm.py`, temperature 0 (fixed in the adapter), max_tokens 600, toolChoice forcing `dispatch_plan`.
- Tool `dispatch_plan` (input schema built from the seed tables): `assignments` (array of {capability: enum of unit capabilities, unit_ids: array of enum of the 22 unit ids}), `hospital` (enum of the 3 hospital names plus "none"), `recalled_facts` (array of short strings). All three are required.
- One attempt per scenario. A transport error (a botocore client or connection error such as throttling, a 5xx or a timeout) may be retried once. A reply that is valid but wrong, or does not follow the schema, is scored as it is and never retried.
- The exact prompt (the same template for all scenarios; the facts are filled in by eval/prompt.py with the formats shown in the template; frozen by this commit):

## 7. Metrics (per configuration, per scenario, then aggregated)
| metric | applies to | definition |
|---|---|---|
| unit_set_match | all 24 | the set of chosen unit ids equals the oracle's set |
| required_covered | all 24 | for every capability in the oracle's effective requirements, the configuration's assignment has at least the required number of distinct available units that really have that capability, and no unit appears twice |
| hazard_unit_included | O1 | HM26 is among the chosen units |
| hospital_correct | scenarios whose incident type has a destination capability | the chosen hospital name equals the oracle's |
| stroke_rule_correct | S1, R03, R10, R17 (strokes) | the chosen hospital equals the oracle's (the bypass rule decides between the two candidates) |
| memory_recall | O2 | the output names both the active hazard kind (`oxygen_storage`) and the earlier incident type (`structure_fire`): A from its recalled hazards and incidents, B always false (it has no memory), C from `recalled_facts` containing "oxygen" and "structure" (case-insensitive) |
| latency | all 24 | A: wall time of `run_call`; B: compute time; C: the Bedrock call latency; median and p95 over the 24 |
| tokens and cost | C | input and output tokens; cost uses the Haiku 4.5 list price from the AWS Bedrock pricing page if it can be reached, otherwise "price not verified" and tokens only |

## 8. Acceptance of the oracle against A (checked first)
A matches the oracle on a scenario when: the chosen unit set is equal, each chosen unit covers the same capability with an ETA within 0.01 s, the hospital (when the type has one) is the same with its ETA within 0.01 s, no unit is unmet where the oracle has none, and for O2 the recalled hazards and incidents equal the oracle's memory. A must match on 24 of 24. If it does not, the run stops at A, the scenario is reported, and B and C are not run (that would be a bug to fix, not a result).

## 9. Reporting rules
- Results are reported exactly as produced. No prompt, scenario, oracle or scoring change is made after this commit.
- Worked examples (3), chosen by rule, not by taste: the first scenario in file order where B's unit set differs from the oracle's; the first where C's unit set or hospital differs; the first where both differ and that was not already chosen. If a category has no case, fewer examples are shown and that is stated.
- Bedrock budget for the whole phase: 26 calls (24 scenarios plus at most 2 transport retries), enforced by `LLM_CALL_CAP=26` in the run process and checked against runs/llm_calls.log.

## 10. Limits of this comparison (stated up front)
- 24 synthetic scenarios in one small area are a demonstration, not a statistical study; there is no confidence interval and a single run at temperature 0.
- The oracle and A share the same rules, written by the same author; the oracle differs in code (it imports nothing from graphdispatch) and in method (haversine snapping, networkx Dijkstra from CSVs), and the advisor confirmed its numbers independently, but it is not a second opinion about whether the rules are medically right.
- C is given facts but no road network by design. Its failures measure what coordinates in text can and cannot support; they say nothing about what a model with a routing tool could do.
- Synthetic units, incident types, hazards and callers throughout.
